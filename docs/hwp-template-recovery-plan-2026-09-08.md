## 1. 복구 전 상태 보존

에이전트가 확인할 항목:
- 검증 API 8002·Frontend 3002·HWP Worker 8000의 실제 PID/실행 경로, PostgreSQL 작업 상태, Worker 내부 큐 상태를 재조회한다.
- 실행 표식 원본과 해시, 관련 작업번호·오류 코드·기존 출력 파일 목록 및 해시를 보존한다. 토큰·문서 본문은 진단 로그에 기록하지 않는다.
- 새로운 HWP 요청을 보류하고 기존 실행 여부를 확인한다. 응답 시간 초과를 작업 종료로 해석하지 않는다.

담당자가 확인할 항목:
- 현재 한글 창의 인증·보안 안내·오류·미저장 문서와 기존 생성 파일 상태를 확인한다.
- 기존 파일이 정상 저장됐는지, 실행 중인 한글 작업이 없는지 확인 의견을 남긴다. 확인이 불가능하면 복구 차단을 유지한다.

통과 조건: 관련 작업과 파일의 상태가 식별되고 실제 한글 창 확인이 끝남. 표식만 보고 통과시키지 않는다.

## 2. Worker 복구 및 원문 읽기

1. 확인된 HWP Worker만 정상 종료한다. 현재 Worker와 표식의 원래 PID 모두 확인하고 사용자 한글 프로세스 일괄 종료는 하지 않는다.
2. `python -m api.hwp_worker --recovery-status`로 그 시점의 표식 해시를 다시 읽는다.
3. 담당자 확인을 받은 후에만 `--confirm-recovery --expected-marker-sha256 <현재 해시> --note <실제 확인 내용>`을 실행한다. 표식 손상·해시 변경·PID 확인 불가 시 중단한다.
4. 원본 표식과 확인 의견이 `.hwp-recovery`에 보존됐는지 확인한 뒤 동일 토큰·허용 폴더로 Worker 하나를 실행한다.
5. 인증된 health, 내부 큐 유휴, `recovery_required=false`를 확인한다. 인증 없는 요청은 401이어야 한다.
6. 해당 공고의 미확인 HWP 제안요청서를 1회 읽어 본문과 원본 해시 불변을 확인한다. 추출 결과를 사람이 원문과 대조하고 공고 지정 제출 양식의 유무를 먼저 확인한다.

통과 조건: 복구 이력 보존, 인증 정상, 실제 원문 열기·닫기·종료 확인, 원본 훼손 없음. health의 `generation_verified:false`는 유지되는 정상 설계이며 생성 성공 여부 판정에 사용하지 않는다.

## 3. 템플릿 2종 준비와 매핑 보완

대상 경로:
- `C:/Users/junpr/autojebi/data/templates/입찰참가신청서_양식.hwp`
- `C:/Users/junpr/autojebi/data/templates/제안서_양식.hwp`

공고에 지정된 양식이 있으면 우선 사용한다. 없는 경우 만든 공통 양식은 검토용이며 공식 제출 적합성을 자동 보장하지 않는다. 원본과 작업용 복사본을 분리하고 기존 파일은 덮어쓰지 않는다.

- 입찰참가신청서: 현재 활성 매핑과 동일한 회사·대표자·주소·공고 필드를 한글에서 삽입한다. 실제 회사정보가 없으면 미입력으로 유지한다.
- 제안서: 공고 지정 구성과 원문 요구사항을 반영하고, 전체 본문 필드 `proposal_body`를 `proposal.body`에 연결한다. 전체 본문에는 `transform=none`과 필수 입력 조건을 적용하며 1,000자 요약으로 대체하지 않는다.
- 요약용 필드는 요약임을 구분하고 회사명·공고명 등 기존 매핑의 필수 여부와 변환을 유지·검토한다.
- 템플릿 버전·파일 해시·필드 목록·필수 여부·본문 매핑을 한 묶음으로 기록한다. 매핑 변경은 검증 DB에서 수행하고 기존 회사정보·수동 설정을 seed로 초기화하지 않는다.
- 복구 완료 후 `/document/fields`로 실제 필드 목록과 중복 발생 번호를 조회하여 DB 매핑과 대조한다. 필수 매핑 필드 누락은 생성 차단, 미매핑 필드는 담당자 검토 대상으로 분리한다.
- 작업대 필수조건에 전체 본문 연결 및 필드 대조 결과를 추가하는 보완을 계획한다. 확인 결과는 템플릿 해시·매핑 버전에 연결하고 변경 시 무효화한다. 원문/회사정보 변경과 마찬가지로 동기화와 재점검을 요구한다.

통과 조건: 두 양식이 실제 한글에서 열리고 필수 필드가 존재하며 제안서 전체 본문이 절단 없이 매핑됨. 파일 존재 또는 OLE/ZIP 구조 검사만으로 통과시키지 않는다.

## 4. 실제 생성 및 사람 검토

1. 합성 시험값을 별도 파일로 준비한다. 한글, 줄바꿈, 긴 공고명, 1,000자 초과 본문, 빈 선택값, 중복 필드를 포함한다. 회사 자격과 실제 금액을 임의 작성하지 않는다.
2. 두 템플릿을 한 번에 하나씩 검증한다. 기존 `tests/test_hwp_worker_live.py`를 `HWP_LIVE_SMOKE=true`, 템플릿·입력값·허용 출력 루트를 지정한 명시 실행으로 사용한다.
3. 입력 필드의 `replaced/missing/remaining_placeholders`, 템플릿·출력 해시, 저장 후 재개방·전체 필드 재조회 결과를 대조한다.
4. 담당자가 생성 HWP를 실제로 열어 글꼴·한글·줄바꿈·표 셀·페이지 나눔·잘림과 긴 본문 전체를 확인한다. 자동 저장값 검증과 별도 확인표로 기록한다.
5. 실제 공고 작업대에서 입력값 확인 → 필수조건 점검 → 사람 생성 요청 → 생성 job·다운로드 → 검토 기록까지 연결한다. 합성 시험 산출물을 실제 공고의 증빙이나 최종 승인으로 승계하지 않는다.

완료 조건: 템플릿 2종 각각 저장값 검증 통과, 필수 누락·잔여 필드 0개, 원본 해시 불변, 사람 배치 검토 완료. 회사 증빙·규격 검토가 부족하면 검토용 초안으로만 유지한다.

## 실패·회귀 검증

- 토큰 누락/불일치, 템플릿 없음/허용 폴더 밖/잘못된 형식, 실제 필드 누락, 본문 미매핑, 입력/템플릿 버전 변경 시 차단을 검증한다.
- 복구 표식 해시 불일치·원래 PID 생존·현재 Worker 실행 중·미확인 한글 창 상황에서는 복구를 진행하지 않는다.
- 시간 초과·저장 실패·재조회 불일치는 성공으로 표시하지 않고 기존 파일과 실패 표식을 보존한다. 원인 재확인 후 새 작업번호·새 출력 경로로만 재개한다.
- 단일 큐/COM 직렬화·중복 요청·실패 승인 거부는 기존 모의 테스트와 회귀 테스트로 확인한다. 실제 한글에 장애를 강제로 주입하는 시험은 별도 승인 없이는 하지 않는다.
- 작업대 필수조건, 필드 확인/생성 클라이언트, 복구 표식, 저장값 검증의 단위테스트와 mock E2E를 실행하고 실연동 결과를 분리 기록한다.
