## 1단계 변경

- 원본 스냅샷과 변경 감지가 같은 사실 정규화 함수를 사용한다. 정규 컬럼을 원시 응답보다 우선하며 기초금액·개찰·출처·필수 체크리스트 변경도 감지한다.
- 수동 본문 편집과 추출 반영 모두 공통 의존성 무효화를 거친다. 이전 반려는 유지하고 연결 요구사항의 확인 상태 및 섹션 승인은 재검토 대상으로 전환한다.
- 준비 검사에서 원문 인용, 확인된 증빙 인용, 제안값, 위치를 다시 검사한다. 최종 준비 단계에서는 원본 체크섬도 확인한다.
- 제안서의 필수 요구사항 대응 수/누락을 API와 화면에 표시한다. 별도 증빙으로 충족할 항목은 실제 근거와 담당자 사유를 요구한다.
- 섹션 검토에서 요구사항/근거 연결을 수정할 수 있고, 무효한 연결은 승인할 수 없다.

제품 실행 환경의 기본 화면 및 운영 DB는 전환하지 않는다. 기존 검토 보고서는 발견 당시 기록으로 남긴다.

## 2단계 검증

- 검토 요청에 `expected_review_id`를 전달한다. 오래된 창의 변경은 409이며 입력 버전을 불필요하게 올리지 않는다.
- `/v2/jobs/{id}/recover`로 실패·반려·유실 파일을 새 실행에 연결한다. 기존 이력/파일은 보존하고 패키지는 각 종류/템플릿의 최신 생성물을 사용한다. HWP는 Worker 및 기존 파일 확인을 요구한다.
- 완료 영수증을 원자적으로 저장하고 완료 DB 기록만 재시도한다. 재시작 시 영수증을 먼저 복구하며 외부 작업은 다시 호출하지 않는다. 영수증 전 중단은 불확실 상태로 남겨 자동 HWP 재실행을 막는다.
- 실행기 heartbeat와 과거 연결 오류를 화면에 분리 표시한다. 감독 프로세스가 종료된 Worker를 재시작한다. 검증 환경의 유휴 Worker PID 66544를 종료한 뒤 PID 77436으로 재시작, heartbeat 정상 및 restart_count=1을 확인했다.
- 동일 원문·회사·증빙 내용의 호출은 입력 버전이 달라도 합산 2회로 제한한다. 정확히 같은 요청의 정상 결과는 재사용하며, 재분석이 기존 채택·반려를 자동으로 되돌리지 않는다.
- 실제 PostgreSQL에서 Worker 동시 실행 직렬화, 완료 기록 2회 실패 후 단일 실행 유지, 두 창 동시 검토 충돌 차단을 검증했다.
- 실제 브라우저에서 생성/다운로드/dry-run/HWP 차단과 두 창 검토 충돌/반려 후 재생성을 검증했다. 1280px 및 390px 화면을 확인했다.

- `/v2/settings`: G2B 키 등록됨, LLM 키 미등록, HWP 토큰 미등록.
- 사용자가 외부 Worker가 없고 개발이 필요하다고 확인했다. `api/hwp_worker`에 새로 구현했다.
- 한글 2022 실행 파일(12.0.0.535)과 pywin32는 존재한다. 32/64비트 등록을 확인하는 읽기 전용 진단은 `hwp_com_registration_missing`이다. 미설치로 단정하지 않으며, 실제 COM 연결은 아직 통과하지 못했다.
- 사용자에게 한글 직접 실행 및 초기 설정/인증 화면 확인을 요청했다. 보안 설정·레지스트리·한글 인증은 자동 변경하지 않았다.

## 3단계 코드 보완

- 요구사항의 근거 채택과 `compliance`(충족/미충족/미판정)를 분리했다. 필수 항목의 미판정/미충족은 최종 준비 및 제안서 승인에서 차단한다.
- 원화 제안 총액·수량·확인된 견적 인용·의견을 버전 검사와 함께 저장한다. 가격 비교는 기초금액에 한하며, 예산/누락값을 0원으로 대체하지 않는다.
- Qdrant 검색 결과는 참고 후보이며 적합도 점수가 아니다. G2B 자격 조회도 확인 대기 참고자료다. 세 축이 모두 평가된 경우에만 종합 점수를 계산한다. 추가 LLM 호출이나 참가 결정 변경은 없다.
- Qdrant 연결에 10초 timeout과 공개 close 메서드를 추가했다. 현재 클라이언트 1.18.0/서버 1.15.5 호환 경고는 남아 있으며, 운영 서버 변경이나 경고 숨김은 하지 않았다.
- 새 HWP Worker는 인증 우선, 4MB 요청 제한, 허용 경로/링크/기존 출력 거부, 전용 COM 스레드와 Windows 전역 mutex를 사용한다.
- 저장 후 실제 출력 재열기와 중복 필드별 재조회를 구현했다. 호출 측이 파일 구조·템플릿/출력 해시·전체 필드·입력값을 재대조한다. 값이 일치해도 배치 검토와 사람 승인은 별개다.
- COM 시작 전 영속 표식을 남긴다. 실패/중단은 재시작 후에도 차단하며, 종료된 원본 PID·표식 해시·담당자 의견을 확인한 수동 복구 승인과 감사 기록을 요구한다.
- 쓰기 HTTP 요청은 자동 재시도하지 않는다. 대기 중 취소와 실행 중 결과 불확실을 구분한다.
- API 실행 스크립트, 작업 실행기/감독 프로세스, HWP Worker가 `.env`를 읽되 명시된 검증 환경을 우선한다. HWP 회사/필드 seed CLI도 로컬 설정을 읽도록 수정했다.
- 전체 재검증 중 Windows 상태 파일 교체의 일시 권한 거부를 재현했다. 같은 임시 파일의 교체만 최대 5회 재시도하고, 감독 상태 저장 실패로 실행 중 작업을 종료하지 않도록 보완했다. 영구 실패는 정상 저장으로 숨기지 않으며, 해당 회귀 3건과 실행기 묶음 35건을 통과했다.
- 실행 방법, 서비스 도식, 실패/복구, 실제 파일 검증 절차: [HWP Worker 운영 안내](hwp-worker.md).

실제 LLM 성공, 실제 HWP 생성/배치, 공고 3건 원문 대조, 운영 백업/복원 및 전환 승인은 여전히 완료 기준에 남아 있다. 모의 시험 통과로 대신하지 않는다.

### 기본 데이터 재실행 안전성

후속 점검에서 `hwp_fields seed`가 기존 회사정보와 메타데이터, 템플릿 경로, 관리자 매핑 및 비활성 상태를 기본값으로 덮어쓰는 것을 확인했다.
기본 실행은 없는 항목만 추가하도록 변경했다. 기존 회사정보 갱신은 `--update-company-from-env`를 명시해야 하며 비어 있지 않은 설정값만 반영한다.
관리자 템플릿/매핑 수정과 soft-disable은 기본 seed나 회사정보 갱신에서 바뀌지 않는다. 잘못된 transform 및 빈 회사정보 갱신 요청은 트랜잭션 전체를 되돌린다.
SQLite 회귀와 실제 PostgreSQL 임시 스키마 검증을 포함한 관련 12건을 통과했다. PostgreSQL 임시 스키마와 테스트 데이터는 트랜잭션 종료 시 rollback했으며 운영 데이터에 seed를 실행하지 않았다.
