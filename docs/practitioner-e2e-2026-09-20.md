# 실무 흐름 E2E 개선 및 검증 — 2026-09-20

## 실행 범위

검증용 작업대 `http://127.0.0.1:3002/workspace`, API 8002, 분리 실행기(local/external), 인증된 한글 Worker를 실제로 시작했다. 기존 로컬 PostgreSQL의 `autojebi_workspace` 검증 DB를 사용했다. 기본 운영 화면 전환이나 실투찰은 하지 않았다.

실공고는 `R26BK01728736-000`의 저장된 공고·첨부를 사용했다. G2B 최신 정보 재수집, 공급 가능 여부의 사업 판단 또는 담당자의 최종 제출 승인을 대신하지 않았다. 실제 회사의 증빙/최종 제출본을 TEST ONLY 데이터로 대체하지 않았다.

## 발견한 문제와 수정

| 문제 | 수정 및 검증 |
|---|---|
| 첨부 주소가 없는 수동 공고에도 가져오기를 반복 안내 | 원문 파일 등록으로 안내하고 파일 선택 위치까지 연다. 다운로드 실패도 같은 복구 경로를 제공한다. 실제 버튼 클릭으로 파일 입력 포커스를 확인했다. |
| 번호 목록·HWP 표·콜론 없는 기한이 요약에서 누락 | 제출서류 번호 목록/표와 라벨 다음 셀의 기한·예산을 읽는다. 평가 점수/적격 조건도 원문 인용으로 표시한다. CRLF를 LF로 재조합하지 않고 원문 위치로 잘라 정확한 인용을 보존한다. |
| 직접 작성할 문서가 없어도 제안서/HWP 필수 | 현재 원문에 대해 사람이 확인한 비어 있지 않은 첨부·전자제출 계획에 한해 명시적으로 HWP를 생략한다. Excel·증빙·요구사항·파일 검토·마감 검사는 유지한다. |
| 기본 HWP 골격이 일반 제출 서식처럼 보임 | 템플릿의 파일 해시와 출처 기록을 검사한다. 검증 골격 또는 출처 미확인 기본 서식의 출력 승인을 차단한다. 실제 양식의 명시적 원본 등록 경로와 검증 골격 이관 도구를 제공한다. |
| 정상 줄바꿈이 미작성 필드로 판정됨 | Markdown의 줄바꿈/공백을 본문 런에 합쳐 별도의 빈 필드를 만들지 않는다. 본문·스타일·인용 링크와 매니페스트 해시를 보존하며 실제 빈 셀 검사는 유지한다. |

## 실제 공고 화면 검증

- HWP 2개와 PDF 1개에서 본문 추출 → 결과 반영을 실제 버튼과 큐로 완료했다.
- 제출서류 14개, 작성·첨부 후보 14개, 제출 일정 1개, 예산 인용 2개, 평가 기준 인용 3개를 복구했다. API에서 받은 원문에 모든 인용이 정확히 포함됨을 확인했다. 이는 요구사항 전체 추출 완료 판정이 아니다.
- 정품 증명 요구사항 1개를 원문 문맥과 대조해 `pending/unassessed`로 저장했다. 같은 후보는 이미 등록됨으로 표시된다.
- 누락 검사 완료 후 원문 전체 확인·별도 자료·증빙·제안서 대응이 미완료로 남는 것을 확인했다. 실제 공고의 `ready`는 false다.
- 실제 기본 입찰 서식의 필드 검사 결과 11개, 필수 필드 누락 0개를 확인했다. 출처는 미확인 상태로 보존하고 제출용 승인을 차단했다.

본문이 같아 보이는 서로 다른 기간 표현은 자동 통합하지 않는다. 조건별 적용 여부와 별도 원문(`source_needs`) 연결은 담당자가 확인해야 한다.

## 한글 실파일 재생성

`python -m tools.verify_hwp_linebreaks`를 명시적으로 실행했다. 모든 작성은 인증된 Worker의 기존 템플릿 제작·필드 입력 API를 사용했다.

- TEST ONLY 24개 필드 저장 및 재열기 검증 통과.
- LF/CRLF를 포함한 줄바꿈 4개가 입력/재읽기에서 일치.
- 실제 렌더링 3페이지의 해시 확인 및 이미지 직접 확인: 줄 구분, 표, 목록, 한글, 쪽번호 정상.
- 원본 템플릿 불변 확인. 실공고 승인이나 회사 증빙으로 승계하지 않음.
- 증거: `data/workspace/exports/linebreaks-022b743c03d44cbc99d32217455aa6ac/verification.json`, `draft.hwp`, `draft-pages/page-001.png`부터 003까지.

첫 시도에서는 줄바꿈만 있는 필드가 미작성으로 보고되어 검증이 실패했다. 이 실패를 감추지 않고 컴파일러 수정 후 새 파일로 재검증했다. Worker의 빈 필드·저장값 검증을 완화하지 않았다.

## 실제 버튼 기반 완료·무효화 검증

합성 공고 `E2E-ATTACHMENT-ONLY-1789853848995`로 실제 API·DB·실행기를 사용했다. 브라우저의 화면 조작으로만 입력·검토·승인을 수행했으며 API 직접 쓰기로 단계를 건너뛰지 않았다.

1. 공고 수동 등록, TEST ONLY 원문/증빙 PDF 2개 업로드, 실제 추출·반영.
2. 원본 첨부·전자 제출 계획 확인, 증빙 원본 연결, 인용을 연결한 요구사항 검토.
3. HWP 생략을 명시한 출력 계획 저장, 누락 검사 0건.
4. Excel 생성·다운로드 해시 및 원문/증빙 인용 대조·승인.
5. ZIP의 원본 바이트·Excel 포함·누락 목록을 대조한 뒤 제출 준비 확인: **버전 10, ready=true**.
6. 화면에서 증빙 본문을 실제로 변경: **버전 11, ready=false**, 관련 요구사항 검토 대기. 과거 ZIP은 동일 바이트로 다운로드 가능하고 과거 제출 준비 버튼은 비활성.

실행 결과는 1건 통과, 40.3초였다. 이는 합성 자료의 버튼 흐름 실행 시간이며 실무 전체 작업 시간 절감률이 아니다. 390px 화면에서도 가로 넘침 없이 결과를 확인했다.

증거는 `data/workspace/attachment-only-loop/E2E-ATTACHMENT-ONLY-1789853848995/`의 `result.json`, `review-ready.png`, `review-invalidated.png`, `review-mobile.png`, Excel 및 ZIP이다. 마지막 상태는 의도적인 변경 후 재검토 상태이며 성공 이력은 삭제하지 않았다.

재실행: 프론트 디렉터리에서 `E2E_BASE_URL=http://127.0.0.1:3002`, `E2E_API_BASE=http://127.0.0.1:8002`, `E2E_WORKSPACE_V2=true`, `E2E_ATTACHMENT_ONLY=true`를 설정한 뒤 `npx playwright test attachment-only-live.spec.ts --project=workspace-v2`를 실행한다. 실행마다 새 TEST ONLY 공고를 만든다.
