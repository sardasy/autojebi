## 우선 수정 사항

1. **높음: LLM 장애를 비관련 판정으로 저장한다.** `api/services/claude_analyzer.py` 예외 fallback이 0점/비관련을 반환하고, `api/routers/notices.py` 분석 경로가 `analyzed`로 전환한다. 실제 인증 오류가 UI에서는 성공이다. 분석 실패 상태/재시도를 제공하고 유효하지 않은 점수는 알림 라우팅에 사용하지 않아야 한다. 이번 dry-run은 이 점수로 `archived_low`를 만들었다. 이 공고의 실제 부적합 또는 참가 포기 결정이 아니다.
2. **높음: 공고 원문을 회사 제출 증빙으로 인정한다.** `api/services/uploads.py` 사업자 키워드 분류와 첨부 자동 연결 경로를 확인해야 한다. 공고 본문에 사업자등록 조건이 언급되었다고 회사 사업자등록증이 확보된 것은 아니다. 원문 첨부와 회사 증빙을 구분하고 준비완료 전 문서 종류/주체 확인이 필요하다. 이번 기록의 상태만 막힘으로 정정했고 분류 코드 자체는 수정하지 않았다.
3. **중간: 서류 단계 이후 그레이드 버튼이 실패한다.** `api/services/grading_runner.py` 허용 상태에 `documents_analyzed`/`spec_extracted`가 없고 UI는 실행 가능하게 표시한다. 앞 단계 재실행 가능 상태와 UI 조건을 맞춰야 한다.
4. **중간: 수동 Upsert의 기관/마감 정규화가 빠져 있다.** `api/routers/notices.py` `upsert_notice`는 raw만 보존하고 이번 입력의 `ntceInsttNm`/`bidClseDt`를 정규 컬럼에 반영하지 않았다. 목록에서는 미확인인데 HWP context에는 기관 값이 보여 일관성이 없다.
5. **중간: 추출 성공의 의미를 보완해야 한다.** 요구값 1개는 기타 요구사항에 들어간 공고 PDF 일부/파일 저장 문구이며, HILS 제안요청서나 구매규격서의 기술 요구를 읽은 결과가 아니다. 추출 실패 안내문을 근거/요구값에서 제외하고 일반 후보와 실제 원문 추출 결과를 분리해야 한다.
6. **중간: 사전 차단 이력과 실패 설명을 정리해야 한다.** HWP 3개 진입 경로 모두 사전 누락 검증에서 막혀 `hwp_generation_jobs`에는 0건이다. 문서 errors에는 남지만 검토함에는 보이지 않는다. 사전 검증 실패와 Worker 실행 실패를 구분한 이력이 필요하다. 생성/검토의 내부 JSON은 기술 상세로 접어야 한다.
7. **낮음: 연결 상태 문구가 과도하게 낙관적이다.** 관리자 G2B OK는 실제 검색 성공을 보장하지 않았다. 키 등록 여부와 마지막 실제 요청 결과를 구분해야 한다.

## 환경 차단과 미검증 범위

- G2B 실제 검색: 시간 초과. 이번 실행으로 키 오류 또는 나라장터 전체 장애라고 단정하지 않는다. 파일 다운로드 성공은 OpenAPI 검색 복구와 별개다.
- LLM: 인증 수단 미설정 오류를 확인했다. 유효한 키를 노출하거나 임의 값을 넣지 않았다.
- HWP: `http://127.0.0.1:8000` Worker 미연결. 회사 필수값도 부족하다. 사전 검증에서 먼저 막혔으므로 실제 PutFieldText, 필드 잔여 검사, 파일 완성, 성공/경고 작업 승인 흐름은 미검증이다.
- 첨부 4개는 실제 원본이다. 공개 공고서의 게시 확장자 `.hwpx`는 실제 OLE 헤더와 다르며 원본을 변형하지 않았다.
- 생성 초안은 근거 없이 제품 적합성이나 회사 실적을 단정하지 않았다. 실제 기술 적합성, 참가 자격, 가격 적정성은 별도 원문/회사 자료 대조가 필요하다.
- 직접 파일 업로드/공통 문서 연결, 참가 결정 저장, 정상 그레이딩/SKU 추천, 성공 HWP 승인/반려는 이번 실공고 흐름에서 완료하지 않았다. 기존 타 공고의 실패 작업 승인 버튼 비활성 표시는 관찰했지만 이 공고의 승인 테스트로 세지 않는다.
- 실제 G2B 투찰, 금액 입력, 제출, Teams/Slack 실전송은 하지 않았다.
