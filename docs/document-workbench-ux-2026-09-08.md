# 서류 작업대 UX 개선 및 검증 (2026-09-08)

## 적용 범위

검증 환경 `3002/8002`의 네 단계 동선을 유지했다: 공고 찾기 → 공고 서류 검토 → 기존 작성자료와 비교·작성 → 서류 확인. 운영 환경 `3000/8001`은 변경하지 않았다. DB 구조 변경은 없다.

## 보완 내역

- 원문 PDF 또는 추출 본문과 요구사항을 PC에서 나란히 표시한다. 작은 화면에서는 위아래로 배치한다. 파일 등록 영역은 원문 대조 영역 아래로 이동했다.
- PDF 원본은 서버에서 페이지 이미지로 렌더링한다. 브라우저 내장 PDF 프레임이 빈 화면으로 나타나는 문제를 확인한 뒤 교체했다. 페이지 이동, 다운로드, 로딩 및 오류 상태를 제공한다.
- 비교표에 이전 작성자료의 인용과 이번 요구사항의 수량·기간 등 수치를 함께 표시한다. 숫자 비교는 적합 판정이나 근거 승인이 아니다.
- 승인된 제안서 섹션은 읽기 전용으로 시작한다. 수정, 초안 저장, 내용 승인, 수정 요청을 분리하고 섹션별 의견을 받는다.
- 생성 파일별 검토 의견을 제공한다. 모바일에서는 의견 입력칸이 한 줄을 차지하며 버튼은 줄바꿈한다.
- 필수정보 누락은 한글 항목명과 다음 행동으로 표시하고 내부 오류는 기술 상세로 접는다. 처리 중·성공·실패를 서로 다른 문구와 색으로 구분한다.
- 동일한 본문 재추출은 기존 검토를 초기화하지 않는다. 캐시를 재사용하기 전 원본 경로와 해시를 검증한다. 문서 내용이 실제로 바뀌면 연결된 요구사항과 제안서의 검토를 다시 요구한다.
- 관련 없는 기존 작성자료의 추가·변경으로 다른 요구사항 검토를 초기화하지 않는다. 수동 반려는 보존하며, 생성물 승인은 여전히 입력 버전 기준으로 판정한다.

## API 계약

- 제안서 섹션 검토 요청의 `approved`는 `true`(승인), `false`(반려), `null`(초안 저장)을 받는다. `null`은 검토 대기이며 반려로 기록하지 않는다.
- `GET /v2/notices/{notice_no}/documents/{document_id}/preview?page=1`은 PDF 한 페이지를 `image/png`로 반환한다. `X-Page-Count`로 총 페이지 수를 제공한다. 인증, 공고별 문서 소유 범위, 원본 해시, 페이지 범위를 검증한다.
- 기존 문서 다운로드는 첨부 다운로드가 기본이다. `preview=true`일 때 실제 PDF 형식인 파일만 inline PDF로 응답한다.
- 프론트 중계 API는 페이지 수 헤더를 전달한다. 미리보기는 캐시하지 않으며 PDF가 아니거나 렌더링할 수 없는 파일은 명시적으로 실패한다.

## 미완료 및 제한

- HWP는 사업자번호·대표자명·주소·공고 기관 누락으로 `blocked` 처리됐다. 생성 성공이나 실제 한글 배치 검증으로 간주하지 않는다.
- 제안서 본문 검토와 생성 파일 다운로드를 제공하며, 실제 HWP/Excel 파일의 화면 내 배치 미리보기는 이번 범위가 아니다.
- 실제 G2B 검색과 유료 LLM 호출을 이번 회귀 검사에서 새로 실행하지 않았다. 예시 PDF와 로컬 API·DB·작업 실행 프로세스로 검증했다.
- 실제 공고 3건, 회사 자료, Windows HWP 실파일 대조 및 운영 전환은 별도 검증이 필요하다. 제출 준비 상태는 false로 유지됐다.
