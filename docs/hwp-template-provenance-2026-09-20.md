# HWP 템플릿 출처와 검증 골격 격리 — 2026-09-20

기본 템플릿 생성 도구가 만드는 파일은 항목명과 공식 문구가 없는 필드 골격이다. 필드 검사와 생성 테스트에 사용할 수 있지만, 그 결과를 제출용 HWP로 승인하거나 최종 제출 준비 완료로 처리할 수 없다. 저장값 검증 및 페이지 배치 확인과 별도로 이 출처 조건을 서버가 검사한다.

## 저장 및 판정

- 신규 골격 생성은 인증된 Worker의 기존 `/document/create-template`만 사용한다. Worker 자체 구현이나 COM 보안 정책은 변경하지 않았다.
- 도구는 새 HWP를 설치하기 전에 `<파일명>.provenance.json`과 `HWP_TEMPLATE_ROOT/.template-provenance/<파일 SHA-256>.json`에 출처를 기록한다. 덮어쓰지 않는 SHA 기록은 파일명·서식 키 변경 이후에도 같은 내용을 검증 골격으로 식별한다.
- 골격에서 생성한 HWP 결과의 SHA도 검증용 출처로 보존한다. 생성 결과를 다른 서식 키의 템플릿으로 복사해도 제출용 승인 대상이 되지 않는다. 같은 SHA의 검증 골격을 공식 양식으로 승격하는 등록 요청은 거부한다.
- 잘못된 JSON, 모르는 속성, 불일치하는 파일 해시·서식 키, 누락되거나 잘못된 SHA 출처 기록은 생성부터 차단한다. 승인 당시 파일·sidecar·SHA 출처 기록 중 하나가 바뀌면 과거 승인은 최신 제출 준비 판정에 사용할 수 없다. 과거 검토 이력과 다운로드는 유지한다.
- 기본 키 `bid_form`·`proposal`의 기존 파일에 출처 기록이 없으면 `unclassified`다. 생성 테스트는 허용하고 제출용 승인은 차단한다. 파일 크기나 이름만으로 검증 골격 또는 공식 양식이라고 확정하지 않는다.
- 다른 기존 서식의 출처 기록이 없으면 `untracked`로 기존 호환 동작을 보존한다. 이 상태는 공식 양식임을 인증한 상태가 아니다. 알려진 검증 골격의 SHA가 있으면 이 호환 예외를 적용하지 않는다.

`GET /v2/hwp-templates`는 `provenance`를 반환한다. `hwp-context`, 필드 검사 및 HWP 생성 결과는 `template_provenance`를 반환한다. 상태는 `validation_only`, `reviewed_source`, `unclassified`, `untracked`, `invalid`, `unavailable`이며 파일 해시, 두 출처 기록의 해시, 생성/승인 가능 여부와 안내를 포함한다. 기존 `/documents/hwp-templates` 응답은 그대로다. 화면은 검증 골격·출처 미확인을 표시하고 승인 버튼을 차단하며, 서버에서 동일 조건을 다시 검증한다.

## 기존 9월 19일 파일의 확인 및 명시적 이관

기존 두 파일은 이 변경으로 자동 분류하지 않는다. 13,824바이트라는 크기, 기본 서식 키, 필드 수만으로 생성 도구의 산출물임을 입증할 수 없다. 담당자는 당시 생성 결과의 SHA와 현재 파일 SHA, 생성 작업 기록, 필드 목록 및 실제 페이지의 항목명·공식 문구 유무를 대조한다. 이를 확인한 경우에만 아래 명령으로 검증용 출처를 등록한다. 출처가 불명확하면 `unclassified`를 유지한다.

```powershell
python -m tools.prepare_default_hwp_templates --mark-existing-skeleton bid_form --expected-sha256 <확인한현재파일SHA256> --confirm-validation-only
```

이 명령은 등록된 서식의 경로만 사용하고 파일 내용은 수정하지 않는다. 예상 해시가 다르거나 기존 sidecar가 있으면 임의로 덮어쓰지 않는다. `proposal`도 독립적으로 확인해야 한다. 본 구현·격리 테스트에서는 실제 두 파일의 출처 등록이나 운영 DB 변경을 하지 않았다.

## 실제 공식 양식 사용 경로

1. 기존 파일·sidecar·SHA 출처 기록을 백업한다. 공식 양식 원본 또는 담당자가 항목명·공식 문구를 보완한 양식을 마련하고 출처 문서/URL/문서번호를 확인한다. 필드 추가는 기존 `api.hwp_fields prepare-template`와 인증된 Worker 경로를 사용한다.
2. 기존 서식 키에 등록된 파일을 해당 양식으로 교체한다. 기본 키를 계속 사용할 수 있다. 새 파일 SHA를 확인하고 사람이 원본 출처, 항목명, 공식 문구, 필드 배치를 대조한다. 단순 이름 변경이나 SHA만 바꾸는 편집은 원본 확인이 아니다.
3. 로컬 관리자가 아래 명령으로 출처 확인 기록을 등록한다. 이전 sidecar가 있으면 그 현재 SHA도 `--expected-metadata-sha256`으로 명시해야 한다. 이전 기록은 별도 이력 파일로 보존하며, 기존 검증 골격의 SHA 기록은 남는다.

```powershell
python -m tools.prepare_default_hwp_templates --register-source-form bid_form --expected-sha256 <새파일SHA256> --source-reference <출처문서식별자> --reviewer-id <관리자식별자> --review-note <원본대조기록> --labels-and-official-wording-checked
```

4. `reviewed_source` 상태를 확인한 뒤 필드 검사, 재생성, 저장값 검증을 진행한다. 생성된 실제 파일의 내용·표·줄바꿈·쪽 나눔 검토와 작업대 승인 절차는 계속 필요하다. 출처 등록은 작업대의 HWP 승인이나 최종 준비 승인을 대신하지 않는다.

등록은 명시적인 해시 확인과 사람의 검토 선언을 받는 로컬 관리 명령이다. 외부 사이트의 공식성이나 문구를 자동으로 인증하지 않으며, 관리자의 파일시스템 접근 권한은 신뢰 경계다. 작업대 일반 사용자를 위한 파일시스템 관리 API를 추가하지 않았다. 관리 명령의 검토자 기록은 v2 인증 사용자 기록과 구분하며 서버 인증 주체로 소급 생성하지 않는다.

## 보관과 검증 결과

템플릿 파일, sidecar, `.template-provenance` 디렉터리를 함께 백업·복구해야 한다. 런타임 기록에는 로컬 검토자와 원본 식별자가 있으므로 Git에 포함하지 않는다. 파일시스템 관리자가 파일과 모든 출처 이력을 삭제하거나 직접 조작하는 상황까지 막는 서명 저장소는 이 범위에 포함하지 않는다.

- 격리 백엔드·HWP 회귀 및 아키텍처 검사 105건 통과. 원본/metadata 변경, 복사·키 변경, 생성된 골격 복사, 동일 SHA 승격 차단, 공식 양식 교체와 과거 기록 보존을 확인했다.
- 실제 API를 사용하는 SQLite 격리 회귀 5건 통과. HWP 승인 차단, 과거 승인과 경고 없는 패키지로 우회 불가, 정상 출처 등록→파일 검토→ready, 이후 출처 기록 변경 시 ready 해제를 확인했다.
- 프론트 관련 Vitest 65건, 타입 검사 통과. OpenAPI 응답 스냅샷을 갱신하고 추가된 출처 응답 키·시드값 노출을 검사했다.
- 실제 한글 파일 생성·페이지 확인과 로컬 실행 환경 재기동은 별도 라이브 검증 기록으로 관리한다. 이 격리 테스트는 실공고 담당자 최종본 대조를 대체하지 않는다.
