## 1. 확인한 현재 구현과 적용 범위

- `api/workspace/assets.py`, `asset_policy.py`, `frontend/src/components/CompanyAssets.tsx`에 중앙 자료 등록·회사 주체·기간·버전·공고 연결·변경 시 재검토가 있다. 보관소를 다시 만들지 않는다.
- `api/parsing/pdf_text.py`에는 OCR 경로가 있으나 엔진·언어팩·추출 성공이 보장되지는 않는다. OCR 실패 후에도 원본을 사람이 확인해 사실을 기록하는 경로를 추가한다.
- `api/workspace/provenance.py`의 기존 요구사항/증빙 검증과 양식 작성 경로는 본문의 정확한 부분 문자열을 요구한다. 전사 주장 저장만 추가해서는 실제 작성까지 이어지지 않는다. 주장 검증을 실제 증빙 연결·섹션·양식·패키지 소비 경로까지 연결해야 한다.
- 회사 참고자료는 계속 참고용이다. 회사 자료에서 사실을 검토한 것과 특정 공고 요건을 충족한다고 판단한 것은 별개다.
- 이번 문서는 개발/운영 데이터를 변경하지 않는다. 새 스키마를 구현할 때는 Alembic 단일 head, staging 적용·복원 검증, Python/TypeScript/OpenAPI 동기화를 따른다.

## 3. P0 — 측정 준비와 목표 사전 고정

### 담당자와 범위

최소 역할은 개발 책임자 1명과 실제 자료를 판독할 수 있는 실무 검토자 1명이다. 백엔드·프론트·QA는 같은 개발자가 맡을 수 있고 별도 검토자 1명이 있으면 교차 평가한다. 역할 이름을 실제 확보 인원으로 계산하지 않는다. 개발 책임자·자료 제공자·검토자·평가 책임자의 이름과 주당 가용 시간을 먼저 기록한다.

담당자가 없으면 합성 기능 검증까지 진행하고 실무 기준선/가치 평가를 미측정으로 둔다. 개발자 자신의 반복 처리 결과는 편향이 있는 보조 관찰로 표시한다. 개인 인증이 꺼진 호환 모드는 화면·계약 테스트에만 사용하고 새 실제 주장 승인은 서버에서 확인한 reviewer 신원으로 기록한다.

공고는 일반 물품, 소프트웨어/라이선스, 기술평가, 복합 자격, 정정공고를 포함하도록 5건 선정한다. 이 속성들은 겹쳐도 된다. 스캔본 실적증명/직인 계약서 중 하나와 표 형식 재무 수치 자료가 최소 자료 집합에 포함되어야 한다. 자료가 실제 없는 항목은 미확보로 기록하며 합성 문서로 채우지 않는다.

### 측정표

| 파일/양식 | 필수 기록 |
|---|---|
| 공고 선정표 | case_id, 공고번호, 원본 해시 집합, 마감 상태, 정정 이력, 유형, 필요한 회사자료, 담당자 |
| 단계별 시간표 | case_id, 방식, 처리자, 시작/종료, 중단 시간, 단계, 활동 시간, 대기 시간 |
| 누락·수정 기록 | requirement_id/field_id, 발견 단계, 필수 여부, 수정 사유, 원인 근거, 조치 시간 |
| 자료 준비 비용표 | 파일 등록·추출·전사·주장 검토 시간, 최초 사용 공고, 재사용 공고 |
| 사전 평가 규칙 | 목표치, 중단 기준, 지표 정의, 코드/규칙 버전, 확정 시각, 확정자 |

기준선은 5건 모두 조건 파악·요구사항 목록·증빙 검색·제출 전 검토에 한정한다. 초안 작성은 사전에 고른 2건만 별도로 측정한다. 자료 수집 대기, 회사 레지스트리 최초 구축 비용, 한글 배치 확인 시간은 분리 기록한다. 기본 방식에도 같은 원본과 회사자료 접근을 제공하되 구조화된 주장/추천 결과는 제공하지 않는다.

기존 산출물의 독립 대조로 정답표를 만들 수 없는 공고는 누락률 분모가 불명확하다고 표시한다. 도구 결과를 정답표로 사용하지 않는다. 재탐색은 한 번 확인한 예산·납기·평가기준을 위치를 잊어 다시 찾은 행위이며, 의도적인 원문 감사·새 정정본 확인은 따로 센다. HWP 배치 수정률은 배치 검토를 수행한 공고만 분모로 삼는다.

### 평가 규칙 고정 시점

기준선 5건을 측정한 직후, 개선 도구로 공고 A를 처리하기 전에 `evaluation-protocol-v1`을 확정한다. 그 후 목표를 변경하면 새 평가 버전을 열고 이후 건에만 적용한다. 기존 결과도 최초 기준으로 함께 보고한다.

아래 숫자는 사전 확정 회의에 올릴 시작 제안이며 아직 확정된 목표가 아니다.

- 가치 목표: 공고별 대상 단계 활동 시간 절감률의 중앙값 15% 이상. 절감률은 `(기준선 시간 - 도구 시간) / 기준선 시간`으로 계산한다. 기준선 0 또는 누락이면 제외 이유를 기록한다.
- 수정 목표: 필수 오류/누락 증가 0건, 사전 선정한 2건의 초안 수정 활동 시간 합계가 기준선 이하. 기준선 직후 이 목표의 채택 또는 대체 목표치를 확정한다. 수정한 필드 비율과 수정 시간을 각각 보고하며, 자동 입력된 필드 수가 적어 좋아 보이지 않도록 전체 필수 필드 수와 채워진 비율도 함께 기록한다.
- 재탐색 목표: 주요 조건 3종의 재탐색 0회. 강제 원문 대조는 재탐색에 포함하지 않는다.
- 가치 중단 기준: 5건 중 3건 이상에서 사전 정의한 대상 단계 활동 시간이 기준선보다 증가하면 P5의 자동 입력 확대/HWP 기능 투자를 보류하고 상위 원인을 먼저 수정한다.
- 즉시 중단 기준: 원문 없는 확정, 오래된/잘못된 회사 증빙의 유효 판정, 필수 누락을 통과시킨 사례가 발견되면 실제 승인 파일럿을 멈추고 회귀 사례로 고정한다. 미완료/환경 장애는 시간 개선 성공으로 계산하지 않는다.

등록 비용은 숨기지 않는다. 5건의 시간 절약 합계와 신규 자료 등록·전사·검토 비용을 나란히 보고한다. 초기 순효과가 음수라도 재사용 가능성은 별도 논의하되 순이익으로 표현하지 않는다.

## 4. P1 — readiness_issues를 단일 원천으로 만들기

한 도메인 함수가 유형화된 이슈를 계산한다. 각 이슈는 `code`, `scope`, `entity_id`, `blocking`, `message_params`, `next_action`을 가진다. 표시용 문장은 코드/매개변수로 렌더링한다.

`blockers = render_blockers(readiness_issues)`로만 생성한다. 호환 API에 같은 문자열·순서·중복 제거 규칙을 유지하되 별도 판정 코드를 남기지 않는다. 작업대, verify, 패키지 manifest, 화면이 같은 계산 결과/투영을 사용한다. 작업 실행 자체의 예외는 오류 코드로 관리하며 준비 미해결 항목과 혼동하지 않는다.

계산 시점과 입력 버전을 기록하고, 만료처럼 시간에 따라 달라지는 조건은 요청/최종 검토 시 다시 확인한다. 저장된 과거 패키지의 이슈와 검토 기록은 당시 이력으로 보존한다.

필수 사유: 증빙 없음·만료·미검토·주체 불일치, 원문 없음·추출 실패·조건 충돌·별도 자료 미해결, 요구사항 미검토·불충족, 유형 매핑 없음, 사람 판단 필요, 배치 확인 필요, 가격 미확정, 추출 연결 오래됨, 규칙 연결 오래됨.

완료 조건: 새 경로에 문자열 `blockers` 직접 추가 없음, 코드별 메시지/해결 동작 존재, 이전 API 차단 의미 회귀 일치, 문자열 투영과 구조화 결과가 같은 이슈를 나타냄. 안전 합성 테스트는 이 단계부터 CI에 추가한다.

## 5. P2 — 스캔본을 포함한 주장 계약

### 추출 스냅샷

추출 결과는 덮어쓰지 않는다. `extraction_id`, `asset_id`, `asset_version`, `file_sha256`, `extractor_version`, `extractor_config_hash`, `text_sha256`, `structure_sha256`, 본문·페이지/셀 위치·완전성·실패 내역·추출 시각을 저장한다. `company_asset_contents`를 사용한다면 자산당 한 행이 아닌 불변 추출 기록의 집합으로 설계한다.

PDF 원본 페이지 또는 렌더링된 페이지에는 페이지 번호와 렌더 버전·이미지 해시를 연결한다. 원본 파일 다운로드는 계속 가능하다. 파일 해시와 페이지 번호만으로 존재하지 않는 페이지를 지정할 수 없도록 서버가 페이지/영역 범위를 검증한다.

### quote_verified의 의미와 세 가지 경로

`quote_mode = exact | normalized | transcribed`, `quote_verified: boolean`, 주장 검토 상태를 별도로 둔다. `quote_verified`는 인용 연결/전사 대조 확인만 의미하며 사실의 진실성이나 공고 충족을 보증하지 않는다. 서버가 검증 결과로 설정하며 클라이언트가 임의로 true를 보내 승인할 수 없다. 승인에는 별도 reviewer 검토 기록이 필요하다.

| 경로 | 저장할 근거 | 인용 연결 확인 |
|---|---|---|
| exact | 추출 ID·본문 해시·정확한 quote·start/end·위치 | 서버가 원문 부분 문자열과 범위 일치 확인 |
| normalized | 위 정보 + 입력 표현·정규화 버전·원문으로 돌아가는 위치 매핑 | 제한적 정규화 후 유일한 위치가 확인되면 서버가 exact 원문 범위를 저장 |
| transcribed | 원본 해시·페이지/표/영역·전사문·전사 작성자·검토자·시각 | reviewer가 실제 원본 영역과 전사문을 대조한 전용 검토 동작으로 확인 |

전사 경로는 OCR 실패뿐 아니라 부분 추출·쪼개진 표·기타 위치 연결 실패에도 사용한다. 없는 start/end를 만들거나 전사문을 추출 본문에 덧붙여 기존 부분 문자열 검사를 통과시키지 않는다. 전사 수정 시 revision이 올라가고 인용 확인과 승인은 다시 대기 상태가 된다.

스캔본에는 원문 이미지·전사문·구조화된 값을 나란히 보여준다. 숫자의 기준연도, 단위, 부가세, 기간, 제외 조건도 포함해 검토한다. 회사 전체 자료를 자동 승인하지 않고 실제 확인한 사실과 범위만 승인한다. 동일인이 작성·검토할 경우도 실제 신원을 기록하며 평가에서는 독립 검토 여부를 별도 표시한다.

주장별 공통 필드: 안정적인 claim_id와 불변 revision, claim_type, 타입별 검증이 있는 value, 단위·기간·회사/제품 주체, asset_id/version/file_sha256, quote_mode, 위 근거 연결, 검토 상태·서버 사용자·시각·의견. `value`는 임의 JSON으로 방치하지 않고 claim_type별 Pydantic 계약을 둔다. 해당 사항 없는 기준연도/기간은 null로 표현한다.

### 공백·쉼표 정규화 제한

원본 본문과 해시는 변경하지 않는다. 정규화는 새 회사 주장 위치 매칭에만 적용하고 공고 원문 인용·기존 가격 검사·동일 문서 판정의 규칙을 일괄 완화하지 않는다.

- 연속 공백·줄바꿈 차이를 허용하고 원문 오프셋으로 역매핑한다.
- 완전한 숫자 토큰 안의 올바른 천 단위 쉼표만 제거한다. `1,234`와 `1234`는 같은 금액 표현 후보가 될 수 있다.
- 부호·소수점·단위·통화·백분율·기준연도·조건·본문 순서는 보존한다. `1,2`, 서로 다른 표 셀의 `1`과 `234`, `1.5`, `15`, `천원`과 `원`은 임의 통합하지 않는다.
- 분리된 숫자를 합쳐야 한다면 동일 셀/영역임이 검증된 경우만 후보로 제시한다. 여러 위치에 일치하거나 구조 경계가 불명확하면 자동 연결하지 않고 전사/담당자 대조로 보낸다.
- OCR의 O/0, I/1 등 문자 치환과 유사도 임계값은 사용하지 않는다.
- 화면·패키지에 raw_quote와 원문 위치를 보존하며 정규화 결과를 정확한 원문처럼 표시하지 않는다.

### 기존 소비 경로 연결

`claim_reference` 선택 필드를 요구사항 근거와 양식 필드/섹션 작성 출처에 추가한다. 중앙 검증 함수가 주장 revision·원본 해시·추출/페이지 연결·검토 신원·회사 주체·유효기간을 확인한다. 기존 quote 기반 요청은 기존 계약으로 검증한다.

전사 경로에서는 회사 자료에 추출 본문이 없어도 검토된 주장 범위의 근거로 사용할 수 있어야 한다. 이를 위해 `evidence_valid`, `section_valid`, 양식 저장/내보내기, readiness 계산, 패키지 검증의 본문 필수 가정을 함께 점검한다. 공고 원문 전체 확인과 별도 자료 미확보 차단은 유지한다. 한 전사 주장이 승인돼도 문서 전체 추출 실패/미검토 영역 경고는 남긴다.

회사 자료 연결 또는 주장의 중앙 승인은 공고별 `confirmed`, `compliance`, `review_status`, `ready`를 자동 변경하지 않는다. 담당자가 현재 공고의 조건과 대조해 기존 역할에 따라 별도로 기록한다.

### 공고 A 중간 점검

자동 추천 카탈로그를 만들기 전에 다음 전체 흐름을 실행한다. 공고 A는 스캔본/재무 표의 실제 필요 자료를 확인해 기준선 측정 전에 지정한다. 평가 규칙 확정 후 자료 부족이 드러나면 미완료로 기록한다. 교체가 필요하면 사유와 평가 버전을 남기며, 이미 도구로 처리한 건을 독립 검증 건으로 재분류하지 않는다.

1. 실제 원본과 회사 자료를 등록한다.
2. 텍스트·정규화·전사 중 해당 경로로 주장을 저장하고 원본과 대조한다.
3. 기존 수동 연결 UI에 claim_reference를 연결한다.
4. 최소 한 실제 작성 항목에 값을 넣고 저장·재열기·검토 사본 다운로드를 확인한다.
5. 패키지에 원본·주장 revision·정확한 위치 또는 전사 범위·검토 기록이 보존되는지 대조한다.
6. 실제 재무 기준연도/금액 단위·실적 기간/범위·서명된 스캔본에서 스키마가 부족한 항목을 기록한다.

이 단계의 완료는 전사 주장이 등록 화면에서만 승인되는 것으로 인정하지 않는다. 최종 작성/패키지까지 근거를 추적할 수 있어야 한다. 파일/환경/실제 자료가 없으면 해당 부분을 미완료로 표시하고 카탈로그 확장을 보류한다. 한글 배치 확인을 못 하면 데이터 흐름만 통과로 기록하고 제출 가능 판정을 내리지 않는다.

## 6. P3 — 분류 매핑과 읽기 전용 후보

한 카탈로그에 기존 코드·한국어 라벨·자료 역할·연결 가능한 요구사항 유형을 둔다. 프론트와 백엔드의 별도 문자열 목록이 서로 다른 코드로 자라지 않도록 카탈로그 조회 계약을 사용한다. 라벨 문자열로 DB 자료를 검색해 매핑하지 않는다.

실행 보완: 기존 코드·한국어 라벨·자료 역할은 `api/workspace/asset_catalog.py`와
`GET /v2/company-assets`의 `category_catalog`로 먼저 통합했다. 아래 요구사항 유형 예시는 아직 추천 규칙이 아니며,
실제 요구 claim_type·조건 카탈로그는 공고 A 검증 후에 확정한다.

| 자료 코드 | 한국어 라벨 | 기존 역할 | 요구사항 유형 예시 |
|---|---|---|---|
| business_registration | 사업자등록증 | company_evidence | legal_identity, business_category |
| corporate_register | 법인등기부등본 | company_evidence | legal_identity |
| credit_rating | 신용평가서 | company_evidence | credit_rating |
| sme_certificate | 중소기업확인서 | company_evidence | sme_status |
| insurance_payment | 4대보험 완납증명서 | company_evidence | insurance_clearance |
| seal_certificate | 인감증명서 | company_evidence | seal_identity |
| other_evidence | 기타 증빙 | company_evidence | 자동 유형 확정 없음 |
| previous_proposal | 기존 제안서 · 참고용 | company_reference | 증빙 추천 제외, 작성 참고만 |
| product_catalogue | 제품 자료 | product_evidence | product_specification |

새 분류는 A의 실제 필요로 확인한 것만 먼저 추가한다. 수행실적·재무제표·제조사 공급확약·견적 등을 한 번에 모두 구현하지 않는다. 4대보험 완납과 납세 증명을 같은 claim_type으로 혼합하지 않는다. 제품·재무 수치는 모델, 기준연도, 통화/단위, 포함 범위를 비교 조건에 포함한다.

규칙마다 requirement_type, 적용 가능한 category/claim_type, 조건, `rule_id`, `rule_version`, 해당 규칙의 내용 해시를 둔다. 카탈로그 전체 버전도 기록하되 특정 요구사항의 판정 근거는 실제 적용한 규칙 해시에 연결한다.

추천 API는 읽기 전용이다. 유효하고 검토된 exact/normalized/transcribed 주장을 모두 후보로 취급한다. 인용 방식이 transcribed라는 이유만으로 탈락시키지 않으며 화면에 검토 방식을 표시한다. 회사 주체·기간·제품·수치 적용 범위를 통과하지 못한 자료는 적합 후보와 분리해 제외 이유를 제공한다. 추천을 보거나 새로고침해도 공고 상태/입력 버전/승인은 바뀌지 않는다.

## 7. 무효화와 과거 기록 보존

| 변경 | 현재 사용에 대한 처리 | 과거 기록 |
|---|---|---|
| 원본 파일/회사자료의 의미 있는 버전 변경·만료·비활성 | 해당 주장/연결/작성값 재검토 | 당시 원본·검토 기록 보존 |
| 새로운 추출 결과의 활성화 | exact/normalized 연결은 extraction_id 불일치로 오래됨 표시. 같은 문장이어도 새 위치 검증/명시적 재연결 전 현재 입력에 승계하지 않음 | 이전 추출 본문·범위 그대로 보존 |
| 추출기 버전만 배포, 재추출은 안 함 | 불변 과거 추출은 계속 식별 가능. 새 버전 배포만으로 저장 위치를 덮어쓰지 않음 | 과거 extractor_version 보존 |
| transcribed 원본/전사/영역 변경 | 전사 대조와 관련 연결 재검토 | 이전 전사 revision 보존 |
| OCR 재실행, 전사 원본/페이지/영역은 동일 | 전사 주장은 OCR 본문 위치에 의존하지 않으므로 자동 무효화하지 않음. OCR과 전사 값이 충돌하면 별도 이슈 | 두 경로와 충돌 기록 보존 |
| 특정 rule_id의 요구 claim_type/조건 변경 | 그 규칙에 연결된 requirement_type 및 관련 작성/준비 판정을 재검토 | 기존 적용 규칙 해시 보존 |
| 무관한 규칙 또는 표시 라벨 변경 | 영향 없는 승인 유지 | 카탈로그 이력 보존 |

후보 GET에서 승인을 수정하지 않는다. 규칙 활성화는 별도 명시적 변경 작업이며, 영향 대상 목록을 확인하고 재검토 표식을 기록한다. 그 작업이 완료되기 전에도 검증 함수가 rule_hash 불일치를 탐지해 오래된 연결로 준비 완료를 통과시키지 못하게 한다. 추출 스냅샷 활성화에도 동일한 원칙을 적용한다.

## 8. 합성 검증과 실무 평가의 분담

합성 검증은 P1부터 기능과 함께 추가한다. 모든 구현을 끝낸 뒤 한 번에 붙이지 않는다.

| CI/합성 E2E에서 강제 | 실제 담당자 평가에서 확인 |
|---|---|
| 추출 실패 → 자동 부재 확정 금지 | 자동 후보가 놓친 실제 필수 요건 |
| 잘못된 인용 범위/본문 해시/페이지 거부 | 전사 정확성과 원본 판독의 난이도 |
| 천 단위 쉼표 허용, 부호·소수점·단위·셀 경계 오병합 거부 | 재무·실적의 실제 적용 조건 해석 |
| 스캔본 전사 승인 → 수동 근거 연결 → 작성 사본 → 패키지 통과 | 전사·검토 입력 비용과 재사용 가치 |
| 만료·회사 주체 불일치·참고자료의 증빙 판정 차단 | 회사 자료가 실제 요건을 입증하는지 |
| 정정 ZIP/과거 작성 사본의 현재 패키지 편입 차단 | 정정 사항을 이해하고 다시 판단하는 비용 |
| 추출 스냅샷·규칙 변경 후 관련 판정 무효화 | 권장 후보의 유용성·거절 사유 |
| 후보 조회 후 compliance/ready/버전/승인 불변 | 단계별 시간·재탐색·사람 수정·최종 누락 |
| 이슈 투영 일치·동시 버전 충돌·역할 검증 | 문서 배치 오류 및 실제 수정 시간 |

CI 통과는 현장 의미 검토 완료가 아니다. 실제 누락/수정은 독립 원문 대조로 기록한다. '[확인 필요]' 비율은 전체 필수 작성 칸을 분모로 고정하고 사유별로 나눠, 미검토 칸을 숨겨 낮추지 않는다.

## 9. 작업 티켓과 일정 산정

| 티켓 | 선행 | 산출물·완료 근거 |
|---|---|---|
| T00 담당자·자료 접근 확정 | 없음 | 역할별 실제 이름·가용 시간·접근 가능한 실제 자료 |
| T01 5건 선정·축소 기준선 | T00 | 선정표·5건 4단계 시간·2건 초안 기록 |
| T02 가치/중단 기준 잠금 | T01 | 평가 규칙 v1, 확정자·시각·코드/규칙 기준 |
| T03 이슈 단일 원천 | 없음, 측정 병행 가능 | 도메인 계산→API/manifest/문구 투영, 호환 회귀 |
| T04 최소 추출·주장 스키마 | T01 | 불변 추출/claim revision·타입별 value·한글 분류 매핑 |
| T05 exact/normalized/transcribed | T04 | 원문 대조 UI·서버 인용 검증·전사 검토 신원·음성 테스트 |
| T06 기존 작성 경로 연결 | T05 | 본문 없는 전사 근거로도 범위 내 검토 사본/패키지 검증 |
| T07 공고 A 중간 점검 | T02,T03,T06 | 실제 재무/스캔 증빙 수동 연결 전체 흐름과 스키마 결함 목록 |
| T08 규칙/후보 및 무효화 | T07 | 카탈로그 v1·읽기 전용 후보·영향 범위 재검토·합성 E2E |
| T09 B~E 평가·5건 집계 | T08 | 사전 정의 지표·A 별도 표시·자료 구축 비용·중단 판정 |
| T10 자동 입력 확대 | T09 가치 게이트 통과 | 주장 기반 자동 기입, 수정률·근거 추적 회귀 |
| T11 HWP 렌더 추가 투자 | T09 배치 문제 근거 | 인증된 기존 Worker 렌더, 담당자 최종 확인 |

먼저 T00~T02로 실무 투입량을 확인한다. 기준선 1~2일/전체 4주는 약속하지 않는다. 공고 한 건의 대상 단계 측정 후 남은 4건의 시간을 재산정한다. 개발과 검토는 각각 작업량을 기록하고, 총 달력 일정은 두 자원의 가용 시간과 선행 의존성으로 계산한다. 실무자 대기 시간을 개발 공수에 숨기지 않는다.

HWP 투자는 '5건 중 2건에서 배치 오류' 또는 '배치 검토 공고당 15분' 또는 '수정 원인의 20%가 배치'를 초기 판단 제안으로 둔다. 기준선 직후 가치 기준과 함께 정의를 고정하고, 기대 절약 시간과 Windows/한컴 유지비를 비교한 뒤 결정한다. 충족해도 한글 최종 사람 확인을 없애지는 않는다.

## 10. ADR·호환성·제품 설명

다음 ADR에는 주장별 세 가지 인용 모드, 추출 스냅샷과 규칙 해시, 이슈의 단일 원천, 변경 시 영향 범위, 실제 투찰 미지원, 한글 최종 배치 사람 확인을 기록한다. ADR 0002의 기존 원문/인용을 소급 정규화하지 않는다. 본 계획은 해당 ADR을 채택 완료로 표시하지 않는다.

레지스트리와 주장 데이터는 PostgreSQL이 원본이다. Company MCP 등 외부 연결은 실제 자료 확보에 필요할 때만 추가하며 최초 구현의 선행 의존성이 아니다. 새 연결은 승인 근거를 고정할 스냅샷 계약을 따라야 한다.

최초 실행 단위는 T00~T02의 선정·측정·사전 규칙 문서와 T03의 단일 이슈 원천이다. 회사자료·규칙·자동 작성 확대는 공고 A 중간 점검 결과에 맞춰 진행한다.
